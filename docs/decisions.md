# Decisions

Newest first. One line each: date, decision, why.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-10-28 | Billing: one Stripe customer per platform account, one subscription per shop, on the platform's own Stripe account. The first plan gets the free trial with no card; a trial that ends with no card pauses the plan (Stripe's missing-payment-method "pause"), never cancels it. One trial per account. | A press can run several shops on one card; pausing keeps the press's work safe and one card reopens it; one trial per account stops endless free trials. |
| 2026-10-28 | Inside a shop's project the stockroom gets its own named Firestore database (`stockroom`), its own bucket (`<shop id>-stockroom`) and its own Hosting site (`<shop id>-stockroom`), each with its own rules; it keeps the project's Realtime Database (us-central1). The profile names the database and bucket (`stockroom` block). Julian's choice (plan 1.20). | Each app deploys its own rules without merging two rule files, so a stockroom change can never open or close the shop's data, and the shop's (default) database, bucket and site stay the shop's. Realtime Database has no Montréal location. |
| 2026-10-28 | The payment service (2.1) makes direct charges on each press's Standard account. Shops prove who they are with the same per-shop service key as the email service. Events are passed on unsigned and each shop fetches them again through the service. The platform fee is a percentage (application fee), 0% by default, per shop or platform-wide, refunded in proportion unless turned off. | One proof for every platform service; re-fetching means no second secret per shop; the fee answers Julian's 28 October go-ahead without taking anything until it is set. |
| 2026-10-28 | The platform's email service calls Resend's REST API with `fetch` (no package). Shop email goes from the press's own Gmail when connected; otherwise from `notifications@<platform domain>` with the press's name and reply-to. Shops reach the service with their own service key, kept in the registry only as a hash. | No package to update or audit; the press's Gmail keeps its emails in its own name (Julian, 28 October 2026); a per-shop key means one leaked shop can't send as another. |
| 2026-10-28 | Platform settings (name Colophon, prices $29/$19/$39 CAD a month, 14-day trial, platform domain and addresses) are environment settings with defaults in `services/settings.js`; the domain is a placeholder until Julian has one. | One place to change a price or address without a code change; a wrong value is refused rather than charged. |
| 2026-10-27 | The shop maker's payments step takes the press's payment provider. Stripe is built first; Square is planned (2.2b) and refused at sign-up check until it is. The registry row keeps `payments: { provider, accountId }`. | Presses can bring Square as well as Stripe; one step shape means adding Square later is a new provider client, not a new step. |
| 2026-10-27 | Two setup runs on one shop can't overlap: the runner holds a per-shop lock in the registry, renewed each step, lapsing after an hour. | Phase 2 starts runs from sign-up and retries; two at once could make two Stripe accounts or deploy two releases. |
| 2026-10-27 | `setup/` is plain Node 22 ES modules with no packages and no framework, tested with Node's own test runner; Google, the registry and the audit log are passed in to the runner and its steps. | The steps are a list of check-then-act calls; nothing needs a framework, and passing the clients in keeps tests and dry runs from ever calling Google. Decided for `setup/` only. |
| 2026-10-27 | A shop's server details (owner address, sender, site address, allowed web addresses) come from `functions/.env.<project id>` in that shop's project, not from a Firestore document. | Firebase loads the file only for its own project at deploy, the server reads it with no database call or wait, and nothing in the browser can read or change it. The setup script writes it. |
| 2026-10-27 | The product's shop and stockroom are copies in `apps/` of this repo; `LyricalmyricalWebsite` and `lyrical-inventory` are never changed for the product. Replaces "shop and stockroom stay in their own repos". | Owner's choice: the website and stockroom are specific to Lyricalmyrical and must keep working in all circumstances. |
| 2026-10-27 | The public shop profile is a script file (`/shop-profile.js`) that sets `window.__SHOP_PROFILE__`, loaded with `defer` before the app. Server-only values (plan, test mode, Stripe account) stay out of it. | The page has the profile before Firebase starts with no extra wait, and one build serves every shop. |
| 2026-10-27 | Build order is `docs/code-plan.md`, one pull request per line. | Small steps, each keeping the live shop working. |
| 2026-10-27 | One central payment service holds the Stripe platform key; shops never do (`docs/payments.md`). | Connect needs the platform key on every call; one place to protect it, one address for Stripe events. |
| 2026-10-27 | A permanent test shop gets every update first and must complete a test purchase (`docs/test-shop.md`). | Today's checks never pay, so a broken checkout would reach paying presses. |
| 2026-10-27 | Shop setup is numbered, re-runnable steps logged per shop (`docs/shop-setup.md`). | The Phase 1 script becomes the Phase 2 shop maker instead of being written twice. |
| 2026-10-27 | Shop and stockroom stay in their own repos; this repo holds only platform parts. | One codebase to fix, not two; Lyricalmyrical becomes one shop's settings. |
| 2026-10-27 | No monorepo yet. | The two apps use different tools and deploy separately. Revisit if the stockroom moves inside each shop's project. |
| 2026-10-27 | Repo public for now. | Owner's choice; make private before the first paying press. |
